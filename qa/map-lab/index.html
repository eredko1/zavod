    From map data to a walkable place.
    

    This is the current local prototype’s source register and generation contract. Update it when adding a source, changing a rule, or validating a new assumption. Source identifiers and API links below come directly from the code’s registry.
    

    Generator helpBenchmark architectureDocumentationWhat remainsMore data sourcesThird-party toolsSource registerGeometry rulesMerge rulesQueries
    

    1 · CollectChoose an area → query live OSM and NYC APIs → retain original responses and provenance.
    2 · ResolveValidate geometry → convert to metres → classify tags → choose recorded values or explicit defaults.
    3 · GenerateTriangulate footprints and holes → extrude buildings → create road surfaces, curbs, props and estimated terrain.
    4 · Inspect & walkRender with Three.js → toggle sources → inspect attributes and errors → test human-scale movement.
    

    Source data, rule estimates, and visual styling are separate. A recorded footprint does not supply a building height; a road centerline does not supply its surveyed edges. Missing building heights remain errors, not invented buildings.
    

    One page: query → filter → generate → benchmark
    

    Open the local generator. Auto Coney fetches the Coney bounding box from OSM and all nine NYC sources. The initial area is Coney Island. Choose Choose on map, drag the basemap under the highlighted box, select an area size, and choose Use this area, then Fetch area. Scroll or use +/− to zoom the basemap without changing the selected area size; arrow keys pan it. Presets include Coney Island and the next block west. Cancel or Escape discards picker changes. Exact coordinates remain available; address/ZIP search is not included. The picker uses OSM background tiles only while open; those images never supply generated geometry. Tiles use browser HTTP caching and visible attribution under the OSM tile policy. Each side is limited to 5 km for this synchronous local prototype; antimeridian-crossing boxes are not supported. The tile picker covers latitudes within ±85°; exact coordinates support polar areas. Outside the NYC coverage region, only OSM is queried.
    

    Choose boundsLive Overpass / SODA / ArcGIS queries. A new area clears prior sources; each successful response is retained within the new session.
    Inspect 2DPan, zoom, filter sources and OSM categories. Inspect original tags and the merge log. Filtering does not alter source matching.
    Generate 3DThe same responses and filters become basic meshes. Orbit or walk; generation errors list missing heights. No hidden saved-data fetch.
    BenchmarkThree repeated builds with named CPU stages, followed by idle, orbit, walking and running with turns. CPU/GPU p95, frame chart and downloadable raw JSON.
    

    The benchmark button measures the current scene in the same browser context and records its input fingerprint and visible geometry. It freezes controls and cancels if the page becomes hidden. Each repeat rebuilds the current sources and reports build stages separately from warmed render timings. It does not claim cold startup or fresh-context comparisons. Use the command-line harness for offline fixtures, served-asset hashes, fresh contexts, comparisons and optional Chrome traces.
    

    This lab is enabled on Vercel at /qa/map-lab/index.html. Local snapshots and reports in .tmp/ remain excluded from deployment. Run ./qa/serve.sh to use it locally. Both versions query APIs directly from your browser; the authored game remains separate.
    

    Development interfaces
    map-pipeline.js resolves source data identically for 2D and 3D. map-build.js compiles the plan into disposable scene resources and records named stages. map-preview.js and map-world.js expose explicit view APIs. benchmark-runner.js drives those APIs; frame-report-view.js renders the same metrics in this page and saved reports. Future materials and textures belong in the mesh/material stage, with their settings included in benchmark metadata. This pass remains untextured.
    Custom Overpass queries run OSM-only and derive bounds from returned geometry. Transient HTTP 429/502/503/504 and network/time-out failures retry up to three attempts with bounded, cancelable waits; invalid queries and incomplete data remain visible errors.
    What remains
    • Classify LION administrative boundaries separately from physical geometry; thin reference lines may still cross lawns.
    • Isolate the observed GPU timing spikes with controlled traces; no guaranteed 60 FPS capacity has been established.
    • Add a main-game benchmark adapter and deterministic routes for other game maps.
    • Validate elevation datums, bridge/tunnel levels, intersection surfaces, curb ramps and building-part edge cases.
    • Move large area generation into workers/chunks and add cancellation during mesh construction.
    • Add materials, textures, road markings and detailed props only after the geometry and performance gates pass.
    

    

    Benchmark architecture
    

    The page and command-line harness share one measurement runner. The page displays results immediately; downloading JSON is optional. CLI runs add offline fixtures, fresh browser contexts, response hashes and saved reports.
    

    1 · OrchestrateUI or Playwright → shared repeat runner → freeze settings, inputs and camera route.
    2 · Build & replayCompile named geometry stages → wait for assets → first draw → warmup → idle, orbit, walk and run.
    3 · MeasureCPU scopes + asynchronous WebGL GPU queries → raw timings, resource events, scene metadata and route checks.
    4 · ReviewValidate repeats → ECharts stacks and timelines → optional JSON or CLI report artifacts.
    

    FolderResponsibility
    data/API acquisition, bounded retries and geographic bounds.
    pipeline/Normalize, merge and compile selected geometry with named build stages.
    render/Meshes, terrain, Three.js world and walking; no benchmark imports.
    ui/Page state, 2D preview, controls, Help and styles.
    benchmark/Development replay adapter, versioned scenarios, profiler, validation, reports and charts.
    docs/Architecture, pipeline, benchmark instructions, research and historical results.
    

    Everything for this lab lives under qa/map-lab/. Open index.html; application modules are grouped by pipeline stage, automated tests and CLI tools live in tests/, pinned inputs in tests/fixtures/, and guides in docs/. The authored game in src/world/ is separate.
    

    CPU stacks remove nested timing overlap. GPU is an independent duration bar; timings cannot establish synchronized start times or total GPU utilization. Charts load after profiling and are disposed before another run. Fallbacks stay in generation/merge logs. There is no per-stage artifact cache or incremental build system yet.
    

    Runtime modules do not import profiling code. The current live lab remains deployed; an explicit npm release package excludes QA and ECharts. Scenario versions, input hashes and settings identify runs. See the WebGL review for overhead measurements and release isolation.

    Elevation analysis and current use
    The refreshed block query returned 175 spot elevations: 150 ground samples (300000), 20 roof samples (302000), and 5 bridge samples (300020). Ground values span 1.259–3.159 m after converting feet to metres. Median ground elevation is 2.147 m; this becomes local Y=0.
    

    Classify samplesOnly ground subtype 300000 feeds terrain. Roofs and bridges remain separately inspectable markers.
    Estimate groundEstimate shared 5 m grid vertices from four nearest samples with inverse squared-distance weighting; nearest sample beyond 100 m. Interpolate within each grid triangle.
    Place geometryBuild indexed ground directly; project land, road and sidewalk polygons once along the same grid cells and diagonals. Apply display/curb offsets to that shared surface so triangles cannot bleed through. Keep buildings upright.
    Walk on surfacesLook up nearby visible surface triangles through a spatial index, with direct terrain interpolation. Camera remains 1.7 m above that surface.
    

    This is an interpolated estimate, not a surveyed terrain mesh or LiDAR reconstruction. Source spot heights do not measure curb steps. Outside the sampled area, extrapolation is particularly uncertain; the rule is recorded in the generation log. Buildings use recorded ground elevation when available, otherwise an interpolated footprint-center value. Combining building ground elevations and spot samples currently assumes compatible vertical references; per-record datum alignment has not been verified.
    

    NYC’s planimetric capture rules describe feet-based elevation samples and ground/bridge/roof classes. Building footprint metadata distinguishes roof height from base elevation and notes source-dependent accuracy. Ground elevation commonly references NAVD88 for modern measurements, but that should not be assumed uniformly for every historical record.
    

    Source filters hide the resolved geometry. A hidden canonical source does not restore its suppressed duplicate; inspect its members in the merge log, or disable Merge sources to compare original records. Regenerate to apply that choice in 3D.
    

    Merge rules for every feature category
    

    Automatic merging is enabled by default in both viewers. The shared merge-rule registry supplies this section directly. It covers all nine connected NYC datasets, current OSM geometry families, semantic/support records and an explicit fallback for unknown types. Use “Merge sources automatically” to compare resolved geometry with the original overlays. Every original record remains available through source downloads and the merge log.
    

    There is no blanket “NYC wins” rule. Resolve identity first, then choose geometry and each attribute separately. Preserve unique coverage from both sources. Source preferences below are fallback orders, subject to feature-specific validity, quality, observation evidence and logged conflicts.

      Match or preserveConfirmed match → one identity. Unmatched → retain. Ambiguous → preserve records and log the conflict.
      Resolve attributesChoose outline, dimensions and semantics independently. Keep alternative values and their provenance.
      Generate onceSuppress only validated duplicates. Keep uncovered segments, holes, components and separate vertical levels.
      

      

      Matching parameters and resolved-record contract
      

      Initial conservative parameters are versioned in map-merge.js: mutually unique building footprint overlap ≥80% (sampled at 1 m, coarser for large footprints); mutually unique active tree points within 1.5 m; complete curb alignment sampled every metre within 0.35 m; generated row trees excluded within 2 m of individual trees. Ambiguous candidates remain separate. These are matching heuristics, not survey guarantees, and should be calibrated further with reviewed examples. A nearest-neighbor distance alone is evidence for a candidate, not proof of identity.
      

      {
  canonicalId, featureKind, ruleId, ruleVersion,
  members: [{sourceId, datasetId, originalId, snapshotId}],
  match: {status, evidence, alternatives, reviewReason},
  geometry: {source, retainedComponents, suppressedDuplicates},
  attributes: {height: {value, unit, source, estimated, alternatives}},
  issues: [{code, severity, sources, message}]
}
      

      The current merge log exports rule version, parameters, member source IDs and original tags, geometry source, selected attribute provenance, evidence, conflicts and suppressed-record coverage. Query/snapshot provenance is exported alongside it. Original IDs stay namespaced. Canonical IDs use stable source IDs when unique, retaining the geometry suffix where source IDs repeat. LION matches retain their original SegmentID and every alias row. Persistent identity across changes in group membership still needs a saved identity map.
      

      Regression checks must continue to verify: unique records survive; confirmed duplicates render once; close but different objects remain separate; ambiguous one-to-many cases are logged; holes and partially covered segments survive; missing values cannot overwrite valid ones; source fetch order and visibility do not change the resolved result. The renderer must report both resolved-feature counts and original-record coverage so deduplication cannot masquerade as missing data.
      

      Tree comparison, 26 September 2026: OSM returned 134 tree points. The larger NYC query rectangle returned 109 forestry records (83 full trees, 18 retired, 8 stumps). Filtering the NYC records to the same OSM polygon leaves 76 records: 53 full trees, 16 retired and 7 stumps. OSM therefore supplies substantially more tree points in this block. Counts describe the fetched records, not verified present-day tree existence; matching and field verification remain separate steps.
      

      Use stable IDs where genuinely shared; otherwise spatial overlap, distance, type and timestamps inform a match. Record the winning source per attribute and keep disagreements visible. This prevents duplicate buildings or trees while allowing each source to fill a different gap.

      Inspectability and ownership
      The live merge lab displays source activity and resolver decisions as each response arrives, with search, conflict filtering, selected-member inspection and log export. Every fetch retains source ID, dataset ID, query URLs, geographic bounds, fetch time, dataset/metadata update times, and original properties. The 3D plan adds resolved dimensions, estimates, source-linked issues, and coverage statuses: rendered, reference, support, represented, hidden, skipped or error. Per-source downloads retain raw responses and acquisition provenance. The generation log exports settings, acquisition timings, build stages, resolved coverage, merge decisions and issues; terrain samples remain in the elevation source download.
      

      Generation logs record fallback reasons; benchmark reports record named build stages, frame work and source acquisition timings. Raw data, generation logs and benchmark reports have explicit downloads. There is no incremental build system or per-stage artifact cache; that integration is deferred.
      

      Merging runs on all fetched records before visibility filtering. Visibility hides the selected geometry source without changing match decisions. Turn merging off to inspect original overlaps. Building and tree matches, LION aliases, road/path coverage and compatible curbs now resolve automatically; other feature categories preserve unique geometry and relationships rather than forcing an unsafe cross-type match. Conflicts and unimplemented structure-height inference remain explicit.
      

      The lab starts empty. Fetch requests new API data; Generate 3D receives the current in-memory session and filters. There is no separate renderer page or stored handoff. QA scripts explicitly load snapshots for repeatable offline measurements.

Merging preserves those rows as members while displaying one reference line. LION includes non-road features and generic/physical street representations, so row count is not road count.

      These values describe complete features intersecting the preset rectangle; not every segment lies wholly within the block. The official LION metadata defines minimum width as paved width in feet. Geometry has no Z coordinates. LION therefore complements the roadbed polygons; it does not provide curb heights or a more accurate pavement outline.
      

      The adapter queries the DCP LION ArcGIS feature service, first requesting spatially intersecting object IDs, then fetching their GeoJSON through POST batches of 500 with all attributes and WGS84 output. POST avoids the service’s query-string length limit; the source snapshot records request methods and bodies. It validates completeness and caps requests at 10,000 records. It is a different API from the other eight Socrata sources. The service reports a data edit time of 21 August 2026; that is not an observation date for every attribute.
      

      Existing example using NYC sidewalk polygons: Sidewalk Widths NYC and its source code. Future datasets should have separate adapters and explicit merge rules.
