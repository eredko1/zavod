    From map data to a walkable place.
    

    This is the current local prototype’s source register and generation contract. Update it when adding a source, changing a rule, or validating a new assumption. Source identifiers and API links below come directly from the code’s registry.
    

    Generator helpGame integrationBenchmark architectureDocumentationWhat remainsMore data sourcesThird-party toolsSource registerGeometry rulesMerge rulesQueries
    

    1 · CollectChoose an area → query live OSM and registered regional sources → retain original responses and provenance.
    2 · ResolveValidate geometry → convert measured units → confirm duplicates → select supported measurements and retain every unique alternative.
    3 · GenerateApply render rules → record estimates separately → build roofs, roads, supports, tanks and terrain without editing source selections.
    4 · Inspect & walkRender with Three.js → toggle sources → inspect attributes and errors → test human-scale movement.
    

    Source merge only selects actual observations. Rendering owns every estimate, interpolation, extrapolation and visual exclusion. A recorded footprint does not supply a building height; a road centerline does not supply its surveyed edges. Missing measured height stays unknown in merge; rendering may use a logged floor-count estimate, otherwise retain the footprint and report the missing model.
    

    One page: query → filter → generate → benchmark
    

    Open the local generator. Auto Coney fetches the Coney bounding box from OSM and all registered regional sources. The initial area is Coney Island. Choose Choose on map, drag the basemap under the highlighted box, select an area size, and choose Use this area, then Fetch area. Scroll or use +/− to zoom the basemap without changing the selected area size; arrow keys pan it. Presets include Coney Island and the next block west. Cancel or Escape discards picker changes. Exact coordinates remain available; address/ZIP search is not included. The picker uses OSM background tiles only while open; those images never supply generated geometry. Tiles use browser HTTP caching and visible attribution under the OSM tile policy. Each side is limited to  km for this local prototype; antimeridian-crossing boxes are not supported. The tile picker covers latitudes within ±85°; exact coordinates support polar areas. Outside the NYC coverage region, only OSM is queried.
    

    Choose boundsLive Overpass / SODA / ArcGIS / LiDAR requests. A new area clears prior sources; each successful response is retained within the new session.
    Inspect 2DPan, zoom, filter sources and OSM categories. Inspect original tags and separate source/render decisions. Filters select participating providers and restore enabled alternatives.
    Generate 3DThe same responses and filters become basic meshes. Orbit or walk; generation errors list missing heights. No hidden saved-data fetch.
    BenchmarkThree repeated builds with named CPU stages, followed by idle, orbit, walking and running with turns. CPU/GPU p95, frame chart and downloadable raw JSON.
    

    The benchmark button measures the current scene in the same browser context and records its input fingerprint and visible geometry. It freezes controls and cancels if the page becomes hidden. Each repeat rebuilds the current sources and reports build stages separately from warmed render timings. It does not claim cold startup or fresh-context comparisons. Use the command-line harness for offline fixtures, served-asset hashes, fresh contexts, comparisons and optional Chrome traces.
    

    This lab is enabled on Vercel at /qa/map-lab/index.html. Local snapshots and reports in .tmp/ remain excluded from deployment. Run ./qa/serve.sh to use it locally. Both versions query APIs directly from your browser; the authored game remains separate.
    

    Development interfaces
    map-pipeline.js exposes measured source resolution separately from render/render-plan.js, which prepares estimated models only for Generate 3D. Fetch area and the 2D preview resolve source observations without estimates or render exclusions. Source merge remains immutable; all unique observations remain available. map-build.js compiles the plan into disposable scene resources and records named stages. Interactive 3D builds use a module worker, transferable geometry buffers and batched scene restoration; Cancel build retains the previous world until a replacement is complete. Source preview resolution and final scene setup still use the main thread. map-preview.js and map-world.js expose explicit view APIs. benchmark-runner.js drives those APIs; frame-report-view.js renders the same metrics in this page and saved reports. Future materials and textures belong in the mesh/material stage, with their settings included in benchmark metadata. This pass remains untextured.
    Custom Overpass queries run OSM-only and derive bounds from returned geometry. Transient HTTP 429/502/503/504 and network/time-out failures retry up to three attempts with bounded, cancelable waits; invalid queries and incomplete data remain visible errors.

    • Add a main-game benchmark adapter and deterministic routes for other game maps.
    • Validate elevation datums, bridge/tunnel levels, intersection surfaces, curb ramps and building-part edge cases.
    • Measure remaining preview, transfer and scene-restoration costs on large areas; 3D compilation now runs in a cancellable worker.

    Benchmark architecture
    

    The page and command-line harness share one measurement runner. The page displays results immediately; downloading JSON is optional. CLI runs add offline fixtures, fresh browser contexts, response hashes and saved reports.
    

    1 · OrchestrateUI or Playwright → shared repeat runner → freeze settings, inputs and camera route.
    2 · Build & replayCompile named geometry stages → wait for assets → first draw → warmup → idle, orbit, walk and run.
    3 · MeasureCPU scopes + asynchronous WebGL GPU queries → raw timings, resource events, scene metadata and route checks.
    4 · ReviewValidate repeats → ECharts stacks and timelines → optional JSON or CLI report artifacts.
    

    FolderResponsibility
    data/API acquisition, bounded retries and geographic bounds.
    pipeline/Normalize measurements, select/dedupe source records and orchestrate named build stages.
    render/Estimated render models and separate decision logs, meshes, terrain, world and walking; no benchmark imports.
    ui/Page state, 2D preview, controls, Help and styles.
    benchmark/Development replay adapter, versioned scenarios, profiler, validation, reports and charts.
    docs/Architecture, pipeline, benchmark instructions, research and historical results.
    

    Everything for this lab lives under qa/map-lab/. Open index.html; application modules are grouped by pipeline stage, automated tests and CLI tools live in tests/, pinned inputs in tests/fixtures/, and guides in docs/. The authored game in src/world/ is separate.
    

    CPU stacks remove nested timing overlap. GPU is an independent duration bar; timings cannot establish synchronized start times or total GPU utilization. Charts load after profiling and are disposed before another run. Fallbacks stay in generation/merge logs. There is no per-stage artifact cache or incremental build system yet.
    

    Runtime modules do not import profiling code. The current live lab remains deployed; an explicit npm release package excludes QA and ECharts. Scenario versions, input hashes and settings identify runs. See the WebGL review for overhead measurements and release isolation.

    Socrata queries page through 1,000 results at a time, ordered by source identifier and the unique :id tie-breaker, with a -row safety limit; a final empty page confirms completeness at the exact cap, and an extra row rejects the source instead of showing a partial result. This stabilizes ties within an unchanged dataset; API updates during acquisition are not an atomic snapshot. LION uses fixed object-ID batches. Identical rows are deduplicated by properties and geometry; repeated IDs with distinct geometry or attributes remain separate. Render IDs append a canonical geometry/attribute fingerprint. MultiPoint observations use individual point IDs linked to their original record.

    Elevation analysis and current use
    Original ground, roof and bridge samples remain distinct source observations. Only the renderer associates roles and estimates terrain/profiles. The terrain datum is derived from the selected supported ground samples; it is recorded with model provenance.
    

    Classify samplesOnly ground subtype 300000 feeds terrain. Roof samples stay references; bridge samples can constrain compatible deck profiles.
    Estimate groundEstimate shared 5 m grid vertices from four nearest samples with inverse squared-distance weighting; nearest sample beyond 100 m. Interpolate within each grid triangle.
    Place geometryBuild indexed ground directly; project land, road and sidewalk polygons once along the same grid cells and diagonals. Apply display/curb offsets to that shared surface so triangles cannot bleed through. Keep buildings upright.
    Walk on surfacesLook up nearby visible surface triangles through a spatial index, with direct terrain interpolation. The camera keeps eye height above its support; stepping off roofs or decks starts a fall.
    

    This is an interpolated estimate, not a surveyed terrain mesh or LiDAR reconstruction. Source spot heights do not measure curb steps. Outside the sampled area, extrapolation is particularly uncertain; the rule is recorded in the generation log. Buildings use recorded ground elevation when available, otherwise an interpolated footprint-center value. Combining building ground elevations and spot samples currently assumes compatible vertical references; per-record datum alignment has not been verified.
    

    NYC’s planimetric capture rules describe feet-based elevation samples and ground/bridge/roof classes. Building footprint metadata distinguishes roof height from base elevation and notes source-dependent accuracy. Ground elevation commonly references NAVD88 for modern measurements, but that should not be assumed uniformly for every historical record.
    

    Source/category filters select merge inputs and restore enabled alternatives. Regenerate to apply that selection in 3D. Cached world visibility changes presentation only; it does not rerun source selection.

    Source selection and rendering rules
    

    Automatic merging is enabled by default in both viewers. The shared merge-rule registry supplies this section directly. It covers all connected NYC/NYSDOT datasets, current OSM geometry families, semantic/support records and an explicit fallback for unknown types. Use “Merge sources” to compare selected observations with original overlays. Merge selects actual source geometry and measurements; it never generates estimates. The separate render catalog below describes models, interpolation and visual exclusions. Every original record and its full provider snapshot remain available in observation inventories and raw downloads. Native-versus-current building display and tree clearance selection belong to rendering.
    

    There is no blanket “NYC wins” rule. Resolve identity first, then choose geometry and each attribute separately. Preserve unique coverage from both sources. Source preferences below are fallback orders, subject to feature-specific validity, quality, observation evidence and logged conflicts.
    

    Rules shared by every source
      

      Classify & compareCompatible feature kind, metre coordinates, units, level, dates and identity evidence.
      Match or preserveConfirmed match → one identity. Unmatched → retain. Ambiguous → preserve records and log the conflict.
      Resolve attributesChoose measured outline, dimensions and semantics independently. Keep alternative values and their provenance.
      Render selected dataEstimate missing model dimensions separately. Keep all source alternatives, holes, components and vertical levels.
      

      A measured building top with only a lower-floor tag keeps an unknown source base. Rendering estimates the lower height separately and disables a contradictory extrusion or collision proxy. Roof-detail selection is independent of the order of equivalent triangles.
      

      

      Matching parameters and resolved-record contract
      

      Source matching parameters live in map-merge.js, building-match.js and nyc-building-mesh.js. Render spacing/clearance parameters live beside their model helpers. Ambiguous candidates remain separate. These are matching heuristics, not survey guarantees, and should be calibrated further with reviewed examples. A nearest-neighbor distance alone is evidence for a candidate, not proof of identity.
      

      {
  canonicalId, featureKind, ruleId, ruleVersion,
  members: [{sourceId, datasetId, originalId, snapshotId}],
  match: {status, evidence, alternatives, reviewReason},
  geometry: {source, retainedComponents, suppressedDuplicates},
  attributes: {height: {value, unit, source, alternatives}},
  issues: [{code, severity, sources, message}]
}
      

      The 2D merge download contains source decisions only. After Generate 3D, generation downloads contain separate merge and render logs. Source exports stream complete JSON on HTTPS/localhost; keep the page open until the download finishes. The lab download worker handles only attachment URLs and does not cache or proxy source/game requests. Source decisions contain rule version, measured selections, member IDs/tags, geometry provenance, evidence, conflicts and represented coverage. Render decisions contain estimated dimensions, profiles, model constraints, placement and visual exclusions; rendering never edits the merge log. Query/snapshot provenance is exported alongside it. Original IDs stay namespaced. Canonical IDs use stable source IDs when unique, retaining the observation fingerprint where source IDs repeat. LION matches retain their original SegmentID and every alias row. Persistent identity across changes in group membership still needs a saved identity map.
      

      Regression checks must continue to verify: unique records survive; confirmed duplicates render once; close but different objects remain separate; ambiguous one-to-many cases are logged; holes and partially covered segments survive; missing values cannot overwrite valid ones; source fetch order and visibility do not change the resolved result. The renderer must report both resolved-feature counts and original-record coverage so deduplication cannot masquerade as missing data.
      

      Tree counts depend on query bounds, status and source edition. See the archived source comparison and pinned fixture provenance; counts do not establish present-day tree existence.
      

      Use stable IDs where genuinely shared; otherwise spatial overlap, distance, type and timestamps inform a match. Record the winning source per attribute and keep disagreements visible. This prevents duplicate buildings or trees while allowing each source to fill a different gap.

      Inspectability and ownership
      The live merge lab displays source activity and resolver decisions as each response arrives, with search, conflict filtering, selected-member inspection and log export. Every fetch retains source ID, dataset ID, query URLs, geographic bounds, fetch time, dataset/metadata update times, and original properties. Fetch and the 2D preview do not prepare render models. Acquisition failures and preview failures have separate labels; a preview failure leaves completed source data retained. Generate 3D adds resolved dimensions, estimates, source-linked issues, and coverage statuses: rendered, reference, support, represented, hidden, skipped or error. Per-source downloads retain raw responses and acquisition provenance. The generation log exports settings, acquisition timings, build stages, resolved coverage, separate source/render decisions and issues; terrain samples remain in the elevation source download.
      

      Generation logs record fallback reasons; benchmark reports record named build stages, frame work and source acquisition timings. Raw data, generation logs and benchmark reports have explicit downloads. There is no incremental build system or per-stage artifact cache; that integration is deferred.
      

      All fetched records remain in the observation inventory. The source checkboxes select which providers can participate in identity and fidelity selection; excluded providers remain available in their full snapshots. Visibility changes in the generated world hide selected geometry without changing existing match decisions. Turn merging off to inspect original overlaps. Building and tree matches, LION aliases, road/path coverage and compatible curbs resolve automatically; other feature categories preserve unique geometry and relationships rather than forcing an unsafe cross-type match. Conflicts and unimplemented structure-height inference remain explicit.

      These values describe complete features intersecting the preset rectangle; not every segment lies wholly within the block. The official LION metadata defines minimum width as paved width in feet. Geometry has no Z coordinates. LION therefore complements the roadbed polygons; it does not provide curb heights or a more accurate pavement outline.
      

      The adapter queries the DCP LION ArcGIS feature service, first requesting spatially intersecting object IDs, then fetching their GeoJSON through POST batches of 500 with all attributes and WGS84 output. POST avoids the service’s query-string length limit; the source snapshot records request methods and bodies. It validates completeness and caps requests at  records. It is a different API from the Socrata sources. The service reports a data edit time of 21 August 2026; that is not an observation date for every attribute.
      

      Existing example using NYC sidewalk polygons: Sidewalk Widths NYC and its source code. Future datasets should have separate adapters and explicit merge rules.
